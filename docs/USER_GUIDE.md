## 一、两段式流程

```
目的（一段自由文本；网页端也可以拖入 .md 材料，先提炼成目的）
      │
      ▼
   forge          2 人：两次模型调用（人格 + 议题）
                  3–5 人：三次（团队骨架 + 人格 + 议题）
                  全部手写：一次（议题）
      │
      ▼
   蓝图            blueprints/*.json（可读、可改、也可手写人格）
      │
      ▼
    run            逐议题对谈 → 整理 → 仍有分歧就补一轮最终统一 → 成果 + 一页速查 + 对话实录
```

两段之间只通过蓝图通信。`forge` 要花几次模型调用，所以议题不满意时改蓝图 JSON
再 `run` 就行，不用把人格和议题重新生成一遍。

网页端还可以把一份或多份 `.md` / `.txt` 材料直接拖进来：系统会先让模型把材料
提炼成「标题 + 一段目的」，再自动锻造蓝图。材料本身不需要写成「目的」的格式。

人数由你选：默认 2 位，最多 5 位。每个议题的发言顺序是固定的：第 1 位（主提出方）
先开场，之后每轮按蓝图顺序依次发言，第 1 位最后回应。

## 二、安装与配置

需要 Python 3.10–3.14 和 [uv](https://docs.astral.sh/uv/)。

```bash
uv sync
cp .env.example .env      # 把 DEEPSEEK_API_KEY 填进去
```

走的是 OpenAI 兼容协议。换 Kimi / 通义 / 本地 Ollama 只改 `.env` 里两行：

```ini
DEEPSEEK_BASE_URL=https://api.moonshot.cn/v1
DEEPSEEK_MODEL=moonshot-v1-8k
```

模拟模式（`--mock`）不需要 key，也不联网、不花钱；产出的是占位内容。

## 三、命令

### `forge`：目的 → 蓝图

```bash
uv run duo-forge forge --purpose "给刚上班、每天坐十小时的程序员写一份颈椎保养手册"
uv run duo-forge forge --purpose-file my.txt
uv run duo-forge forge --purpose "..." --title 我的手册 --topics 7
uv run duo-forge forge --purpose "..." --people 3
uv run duo-forge forge --purpose "..." --team-hint "要有一个医生、一个患者、一个管理者"
```

| 参数 | 说明 |
|---|---|
| `--purpose` | 一段自由文本，至少 8 字、最多 2000 字 |
| `--purpose-file` | 从文件读目的；文件第一行写成 `# 标题` 时，那一行当标题 |
| `--title` | 成果标题；留空由模型起 |
| `--people` | 对话人数，2–5，默认 2；不给时按人格数组长度推断 |
| `--team-hint` | 团队级分工要求（强偏好），最多 500 字 |
| `--topics` | 生成几个正文议题，默认 5，上限 12 |
| `--out` | 蓝图输出目录，默认 `blueprints/` |
| `--mock` | 离线模拟，不调用真实模型 |
| `--personas-file` | 逐位自定义 2–5 位专家，见第五节 |

产物是 `blueprints/<slug>-<时间戳>.json` 和同名 `.md`。终端最后会打印下一步该敲的
`run` 命令。

### `run`：蓝图 → 成果

```bash
uv run duo-forge run --blueprint blueprints/xxx.json
uv run duo-forge run --purpose "..."          # 先 forge 再跑，顺手把蓝图存下来
```

| 参数 | 说明 |
|---|---|
| `--blueprint` | 用之前 forge 出来的蓝图；和 `--purpose` 二选一 |
| `--purpose` / `--purpose-file` / `--title` | 不传蓝图时，现生成一份 |
| `--people` | 现生成蓝图时用几位专家，2–5 |
| `--team-hint` | 现生成蓝图时的团队级分工要求 |
| `--topics` | 现生成蓝图时用几个议题 |
| `--rounds` | 每个议题的轮数上限，默认 3 |
| `--no-converge` | 关闭所有收敛处理：每个议题跑满轮数，结束后也不做最终统一 |
| `--only` | 只跑指定议题，逗号分隔，例如 `sleep-debt,reality` |
| `--out` | 产物输出目录，默认 `outputs/` |
| `--mock` | 离线模拟 |
| `--personas-file` | 只在 `--purpose` 模式下可用，见第五节 |

用 `--blueprint` 时，人数、人格和团队要求都已经在蓝图里，不能再给
`--people` / `--team-hint` / `--personas-file`。

议题的 `key` 由模型生成，用 `forge` 的输出或 `show` 可以查到。

### `show`：摊开看一份蓝图

```bash
uv run duo-forge show --blueprint blueprints/xxx.json
uv run duo-forge show --blueprint blueprints/xxx.json --json
```

不调用模型。默认打印给人看的版本，`--json` 打印原始 JSON。

## 四、蓝图

蓝图是两段流程之间唯一的接口，也是给人改的。

- **JSON 那份**给机器，也给想动手改议题的人。改完直接 `run --blueprint`。
- **Markdown 那份**给人在阅读器里看：每位专家最终拿到的 system message 一字不差地
  摊开在里面，包括由代码追加的发言纪律。

现在的格式是 **format 2**：`personas` 是 2–5 位的数组，每位带一个短角色名
`role`。顺序有语义：

- 第 1 位是**主提出方**：每个议题由他开场，每轮最后回应；
- 第 2–5 位是**回应者**：按蓝图顺序先发言，负责质疑、补充、指出落不了地的地方。

每位专家的字段是 `role` / `name` / `title` / `stance` / `system_message`。
`name` 必须全队唯一；`role` 可以不写（会按位置补「主提出方 / 专家 N」）。

旧版 **format 1** 的蓝图仍然能读：它必须是两位，角色自动补成「主提出方 / 挑战者」，
不用重新 forge。

> 网页版只跑当次 forge 出来的蓝图。历史蓝图、手改过的蓝图，用命令行的
> `duo-forge run --blueprint`。

## 五、自定义团队与人格

有些目的需要指定专家身份。2–5 位里的每一位都可以独立选择模式；没写的位置交给模型：

| 模式 | 用户提供 | 谁来写 |
|---|---|---|
| `auto`（默认） | 什么都不填 | 模型生成 |
| `hint` | 一两句方向 | 模型展开成完整人格 |
| `manual` | 角色名（可选） / 称呼 / 身份 / 负责什么 / 人格设定 | 用户写死，模型不再生成这一位 |

另外可以给一段**团队级分工要求**（`--team-hint` / 网页文本框 / 人格文件的 `team`）。
它是强偏好：AI 会尽量落实你点名的角色；人数对不上时自行合并或补齐，不会报错。
逐位设置和团队要求冲突时，以逐位设置为准。

### 命令行

`--personas-file` 推荐用数组写法，按位置对应第 1–N 位：

```json
{
  "team": "要有一个一线医生、一个患者、一个管理者",
  "personas": [
    {
      "mode": "manual",
      "role": "主提出方",
      "name": "许医师",
      "title": "三甲医院康复科物理治疗师",
      "stance": "什么是对的",
      "system_message": "【人格】…\n【专业立场】…\n【你的盲区，不要掩饰】…\n【长期背景与案例】…"
    },
    {"mode": "hint", "hint": "一位带过很多程序员的实战派教练"},
    {}
  ]
}
```

```bash
uv run duo-forge forge --purpose "…" --people 3 --personas-file personas.json
```

- 数组可以**短于** `--people`：缺的位置自动交给模型。
- 数组比人数长会报错。
- 没给 `--people` 时，按数组长度推断人数（最少 2）。
- 旧的 `{"proposer": …, "challenger": …}` 写法继续可用；数组和旧键同时出现时，
  **以数组为准**。
- `--team-hint` 覆盖人格文件里的 `team`。
- `run --blueprint` 时人格已经在蓝图里了，不能再给这三个参数中的任何一个。

### 网页

第一步展开「自定义团队与人格（可选）」：

- 顶部是团队分工要求文本框；
- 下面按当前人数动态显示 2–5 个编辑器，每位独立选 auto / hint / manual；
- 减少人数时，被隐藏位置的草稿不会丢，改回去还在；浏览器刷新也不丢。

### 字段与边界

| 字段 | 上限 / 规则 |
|---|---|
| `role` | 12 字，单行，可选（manual）；不写按位置补 |
| `name` | 20 字，单行，必填（manual）；全队唯一 |
| `title` | 60 字，单行，必填（manual） |
| `stance` | 40 字，单行，必填（manual） |
| `system_message` | 12000 字，可多行，必填（manual） |
| `hint` | 300 字，必填（hint） |
| `team` / `--team-hint` | 500 字 |

- 手写的人格设定里**不要写**【发言纪律】【收手纪律】【统一纪律】——这三段由代码追加，写了会重复，
  解析时也会被拒绝。
- **人格记忆**没有单独字段，就是 `system_message` 里的一段长期背景与案例。它会在每个
  议题、每一轮随 system message 发给模型，**越长越贵**。
- 议题生成只看角色 / 称呼 / 身份 / 立场，不看这段背景。想让它影响选题，把要点写进
  `stance` 或目的。
- 全部位置都手写时，`forge` 只调用一次模型（生成议题）；标题优先用 `--title`（或网页上的
  标题），没给就用「对谈成果」。
- 3–5 人时，模型生成人格要走两次调用：先出团队分工骨架，再展开完整人格。这是为了
  避免五个人换汤不换药。

## 六、网页版

```bash
./run.sh                  # 起服务并自动打开浏览器
./run.sh --mock           # 页面默认勾上模拟模式，不花钱
./run.sh --port 9000      # 换端口，默认 8785（被占用会往后顺延）
```

流程是**目的 → 锻造蓝图 → 审阅/勾选议题 → 开始对谈**。网页和命令行走的是同一套
`authoring` / `pipeline`，没有第二套业务逻辑。

第一步顶部的「对话人数」选 2–5。锻造后第 2 步会列出全部参与者、角色和分工；
审阅阶段只读，想换人或改分工就回第 1 步重新 forge。

### 拖入 .md / .txt 材料

第一步的目的输入框下方有一条拖放提示，也可以点「选择文件」。把一份或多份
`.md` / `.markdown` / `.txt` 拖进第一步卡片后，会自动：

1. 在浏览器里读取并按拖入/选择顺序合并材料；
2. 多花**一次模型调用**，把材料提炼成「标题 + 一段不超过 2000 字的目的」；
3. 用提炼出的目的自动锻造蓝图，**停在第二步审阅**，不会自动开始对谈。

提炼出的标题和目的会回填到输入框；材料框里能看到文件名、字数和一个开头预览。
想调整就改目的/标题/人数/人格，再点「锻造蓝图」重新 forge——这时不会再次发送材料。
想换材料就重新拖一次。

边界：

- 只收文本类文件：`.md` / `.markdown` / `.txt`；单份不超过 512 KB，
  一次最多 20 份，合并后不超过 30000 字。请使用 UTF-8 编码，其他编码会提示乱码。
- 材料内容会发给模型用于提炼目的；蓝图里只保存提炼后的目的，不保存材料原文。
- 模拟模式下，提炼和后续锻造都会走同一条链路，但产出是占位内容。
- 拖入材料时，`forge` 的调用次数会在「材料提炼」之外再走正常的人格/议题流程；
  页面上的成本提示会按当前人数和手写情况算出来。

首次在 WSL 里建桌面快捷方式（之后双击桌面上的「智能体人格与议题生成器」）：

```bash
uv run python make_shortcut.py
```

几个边界：

- **单实例**：重复双击/启动只会把浏览器指到已经在跑的那个，不会起第二个服务。
- **重启才生效**：改了代码后要关掉旧进程再启动；单实例探测不会热加载。
- **停止掐不断模型调用**：锻造会在调用返回后丢弃结果，对谈会在当前这一轮结束后收手。
- 网页版只跑当次 forge 出来的蓝图；历史蓝图用命令行。
- `.lnk` 内嵌本机发行版名和绝对路径，所以不入库；换台机器重新跑一次
  `make_shortcut.py`。

## 七、产物

跑完 `run` 后，`outputs/` 下有三份：

| 文件 | 内容 |
|---|---|
| `handbook-<时间戳>-<slug>.md` | **最终成果** |
| `quick-<时间戳>-<slug>.md` | **一页速查版**，从上面那份压出来的 |
| `transcript-<时间戳>-<slug>.md` | 全部专家的完整对话实录 |

模拟模式产出的文件带 `.mock` 后缀、开头有醒目警告——**那份是占位内容，没有参考价值**，
用途只是确认代码链路是通的。

成果文件开头会列出全部参与者和各自角色；2 人时正文的分歧小节叫「两人分歧」，
3–5 人时叫「各方分歧」，按人逐条列出立场。全部议题结束后若还有未统一的分歧，
会多出一节 **附录 D · 最终统一意见**，写清统一结论和仍然保留意见的人。

## 八、提前收手与最终统一

### 提前收手

`--rounds` 是**上限**，不是定额。**所有回应者**在同一轮都明确表示对当前方案已经没有
新的反对意见时，那个议题就在轮次边界提前收手。终端和实录里会写明第几轮收的。

- 2 人模式下回应者只有挑战者，所以判据就是「挑战者无异议」。
- 至少跑满 2 轮才会允许收手；第 1 轮是结构上最小的有效交锋。
- 只要还有一位回应者提出新意见，讨论就继续。
- 模拟模式下收手**恒关**：mock 的职责就是证明循环确实跑满了 N 轮。
- 判定用完全相等，不是包含。模型写「【无异议】不过还有两点」时，辩论继续。

### 全部议题结束后的最终统一

全部议题（含收尾议题）跑完后，整理环节会在每节和附录 A 的最后标一个分歧状态。
只要有任何一处标着「有」，系统就会**再跑一轮、固定只有这一轮**：

1. 把最终成果里的「各节要点 + 各节分歧 + 附录 A」摘要发给所有专家；
2. 回应者先表态：接受就只回「【无异议】」，不接受就只留**最后一条**修正；
3. 主提出方最后听完所有人，给出**最终统一结论**。

成果里会多出 **附录 D · 最终统一意见**，分两块：

- **统一结论**：哪些按原方案定稿、采纳了谁的修正；
- **保留意见**：仍然没被说服的回应者，逐条附上原话。**不会因为「要统一」就把
  真实反对抹掉**——统一结论和保留意见并存，读者自己判断。

没有分歧（每节和附录 A 都标「无」）、`--no-converge`、或模拟模式下，这一轮不跑。
一轮之后还没谈拢，也不再追加第二轮。

代价：不会按议题逐个追加；只在全部议题结束后**最多多一次「人数」次调用**
（2 人 2 次，5 人 5 次）。速查版仍是一次调用，不受影响。

### 开关

- `--no-converge` 一键关掉这两件事：每个议题跑满轮数，全部议题结束后也不做统一。
- 网页版对应上面的「谈拢了就收手，最后强制统一」勾选框。
- 模拟模式下两件都**恒关**：mock 只证明链路通，不做真实收敛判断。

## 九、注意与常见问题

**一次真实运行要花多少次调用？**

每个议题：每轮 **人数** 次发言 + 1 次整理；最后再花 1 次压速查。开场白不花调用。
全部议题结束后，如果成果里仍有未统一的分歧，会再花最多 **人数** 次做一轮强制统一。
`forge` 正常：2 人 2 次（人格 + 议题）；3–5 人 3 次（团队骨架 + 人格 + 议题）；
全部手写 1 次（议题）。网页拖入材料时再多 1 次「材料提炼」。提前收手会让实际
次数少于上限。

**为什么模拟模式跑得很慢/很假？**

模拟后端只吐固定模板，用来验证链路，不是真实内容。真实内容要把 `.env` 里的
`DEEPSEEK_API_KEY` 填好，并去掉 `--mock`。

**forge 偶尔会重试？**

生成那一步要求模型输出 JSON。格式不对时，`authoring` 会把具体错误拼回提示词、
用同一个 agent 再要一次；两次都错才失败。小模型触发重试更频繁，属正常现象。

**换了模型之后生成质量差？**

生成那一步对 JSON 的服从度比较吃模型能力。对谈环节对模型宽松一些。换模型时优先保证
`forge` 稳定。

**网络/超时问题？**

真实后端已经注入了不联网的 token 计数器并设了超时，避免 camel 默认计数器联网下载
词表时卡住。细节见 [ENGINEERING.md](ENGINEERING.md) 的踩坑记录。
