## 一、两段式流程

```
目的（一段自由文本）
      │
      ▼
   forge          两次模型调用：设计两位专家 + 生成一组议题
      │
      ▼
   蓝图            blueprints/*.json（可读、可改、也可手写人格）
      │
      ▼
    run            逐议题对谈 → 整理 → 成果 + 一页速查 + 对话实录
```

两段之间只通过蓝图通信。`forge` 要花两次模型调用，所以议题不满意时改蓝图 JSON
再 `run` 就行，不用把人格和议题重新生成一遍。

---

## 二、安装与配置

需要 Python 3.10–3.14 和 [uv](https://docs.astral.sh/uv/)。

```bash
uv sync
cp .env.example .env      # 把 DEEPSEEK_API_KEY 填进去
```

走的是 OpenAI 兼容协议。换 Kimi / 通义 / 本地 Ollama 只改 `.env` 里两行：

```ini
DEEPSEEK_BASE_URL=https://api.moonshot.cn/v1
DEEPSEEK_MODEL=moonshot-v1-8k
```

模拟模式（`--mock`）不需要 key，也不联网、不花钱；产出的是占位内容。

## 三、命令

### `forge`：目的 → 蓝图

```bash
uv run duo-forge forge --purpose "给刚上班、每天坐十小时的程序员写一份颈椎保养手册"
uv run duo-forge forge --purpose-file my.txt
uv run duo-forge forge --purpose "..." --title 我的手册 --topics 7
```

| 参数 | 说明 |
|---|---|
| `--purpose` | 一段自由文本，至少 8 字、最多 2000 字 |
| `--purpose-file` | 从文件读目的；文件第一行写成 `# 标题` 时，那一行当标题 |
| `--title` | 成果标题；留空由模型起 |
| `--topics` | 生成几个正文议题，默认 5，上限 12 |
| `--out` | 蓝图输出目录，默认 `blueprints/` |
| `--mock` | 离线模拟，不调用真实模型 |
| `--personas-file` | 自定义一位或两位专家，见第五节 |

产物是 `blueprints/<slug>-<时间戳>.json` 和同名 `.md`。终端最后会打印下一步该敲的
`run` 命令。

### `run`：蓝图 → 成果

```bash
uv run duo-forge run --blueprint blueprints/xxx.json
uv run duo-forge run --purpose "..."          # 先 forge 再跑，顺手把蓝图存下来
```

| 参数 | 说明 |
|---|---|
| `--blueprint` | 用之前 forge 出来的蓝图；和 `--purpose` 二选一 |
| `--purpose` / `--purpose-file` / `--title` | 不传蓝图时，现生成一份 |
| `--topics` | 现生成蓝图时用几个议题 |
| `--rounds` | 每个议题的轮数上限，默认 3 |
| `--no-converge` | 不做提前收手判断，每个议题跑满轮数 |
| `--only` | 只跑指定议题，逗号分隔，例如 `sleep-debt,reality` |
| `--out` | 产物输出目录，默认 `outputs/` |
| `--mock` | 离线模拟 |
| `--personas-file` | 只在 `--purpose` 模式下可用，见第五节 |

议题的 `key` 由模型生成，用 `forge` 的输出或 `show` 可以查到。

### `show`：摊开看一份蓝图

```bash
uv run duo-forge show --blueprint blueprints/xxx.json
uv run duo-forge show --blueprint blueprints/xxx.json --json
```

不调用模型。默认打印给人看的版本，`--json` 打印原始 JSON。

## 四、蓝图

蓝图是两段流程之间唯一的接口，也是给人改的。

- **JSON 那份**给机器，也给想动手改议题的人。改完直接 `run --blueprint`。
- **Markdown 那份**给人在阅读器里看：两位专家最终拿到的 system message 一字不差地
  摊开在里面，包括由代码追加的发言纪律。

两位专家的字段是 `name` / `title` / `stance` / `system_message`，顺序有语义：
第一位是方案提出方（先开口），第二位是挑战者（负责挑刺）。

> 网页版只跑当次 forge 出来的蓝图。历史蓝图、手改过的蓝图，用命令行的
> `duo-forge run --blueprint`。

## 五、自定义人格

有些目的需要指定专家身份。`forge` 允许按需自定义**一位或两位**，每位独立选择模式：

| 模式 | 用户提供 | 谁来写 |
|---|---|---|
| `auto`（默认） | 什么都不填 | 模型生成 |
| `hint` | 一两句方向 | 模型展开成完整人格 |
| `manual` | 称呼 / 身份 / 负责什么 / 人格设定 | 用户写死，模型不再生成这一位 |

### 命令行

用 `--personas-file` 给一个 JSON。某一侧留空、省略或写成 `{}` 都表示交给模型：

```json
{
  "proposer": {
    "mode": "manual",
    "name": "许医师",
    "title": "三甲医院康复科物理治疗师",
    "stance": "什么是对的",
    "system_message": "【人格】…\n【专业立场】…\n【你的盲区，不要掩饰】…\n【长期背景与案例】…"
  },
  "challenger": {"mode": "hint", "hint": "一位带过很多程序员的实战派教练"}
}
```

```bash
uv run duo-forge forge --purpose "…" --personas-file personas.json
```

`run --blueprint` 时人格已经在蓝图里了，不能再给 `--personas-file`。

### 网页

第一步展开「自定义人格（可选）」，两位专家各自选模式并填写。草稿存在浏览器里，
刷新不丢。

### 字段与边界

| 字段 | 上限 / 规则 |
|---|---|
| `name` | 20 字，单行，必填（manual） |
| `title` | 60 字，单行，必填（manual） |
| `stance` | 40 字，单行，必填（manual） |
| `system_message` | 12000 字，可多行，必填（manual） |
| `hint` | 300 字，必填（hint） |

- 手写的人格设定里**不要写**【发言纪律】【收手纪律】——这两段由代码追加，写了会重复，
  解析时也会被拒绝。
- **人格记忆**没有单独字段，就是 `system_message` 里的一段长期背景与案例。它会在每个
  议题、每一轮随 system message 发给模型，**越长越贵**。
- 议题生成只看称呼 / 身份 / 立场，不看这段背景。想让它影响选题，把要点写进 `stance`
  或目的。
- 两位都手写时，`forge` 只调用一次模型（生成议题）；标题优先用 `--title`（或网页上的
  标题），没给就用「对谈成果」。

## 六、网页版

```bash
./run.sh                  # 起服务并自动打开浏览器
./run.sh --mock           # 页面默认勾上模拟模式，不花钱
./run.sh --port 9000      # 换端口，默认 8785（被占用会往后顺延）
```

流程是**目的 → 锻造蓝图 → 审阅/勾选议题 → 开始对谈**。网页和命令行走的是同一套
`authoring` / `pipeline`，没有第二套业务逻辑。

首次在 WSL 里建桌面快捷方式（之后双击桌面上的「智能体人格与议题生成器」）：

```bash
uv run python make_shortcut.py
```

几个边界：

- **单实例**：重复双击/启动只会把浏览器指到已经在跑的那个，不会起第二个服务。
- **重启才生效**：改了代码后要关掉旧进程再启动；单实例探测不会热加载。
- **停止掐不断模型调用**：锻造会在调用返回后丢弃结果，对谈会在当前这一轮结束后收手。
- 网页版只跑当次 forge 出来的蓝图；历史蓝图用命令行。
- `.lnk` 内嵌本机发行版名和绝对路径，所以不入库；换台机器重新跑一次
  `make_shortcut.py`。

## 七、产物

跑完 `run` 后，`outputs/` 下有三份：

| 文件 | 内容 |
|---|---|
| `handbook-<时间戳>-<slug>.md` | **最终成果** |
| `quick-<时间戳>-<slug>.md` | **一页速查版**，从上面那份压出来的 |
| `transcript-<时间戳>-<slug>.md` | 两位专家的完整对话实录 |

模拟模式产出的文件带 `.mock` 后缀、开头有醒目警告——**那份是占位内容，没有参考价值**，
用途只是确认代码链路是通的。

## 八、提前收手

`--rounds` 是**上限**，不是定额。挑刺那位（挑战者）明确表示对当前方案已经没有新的
反对意见时，那个议题就在轮次边界提前收手。终端和实录里会写明第几轮收的。

- 至少跑满 2 轮才会允许收手；第 1 轮是结构上最小的有效交锋。
- `--no-converge` 一键回到死板跑满。
- 模拟模式下收手**恒关**：mock 的职责就是证明循环确实跑满了 N 轮。
- 判定用完全相等，不是包含。模型写「【无异议】不过还有两点」时，辩论继续。

## 九、注意与常见问题

**一次真实运行要花多少次调用？**

每个议题：每轮 2 次发言 + 1 次整理；最后再花 1 次压速查。开场白不花调用。
`forge` 正常 2 次（人格 + 议题），只自定义一位仍 2 次，两位都手写只 1 次。
提前收手会让实际次数少于上限。

**为什么模拟模式跑得很慢/很假？**

模拟后端只吐固定模板，用来验证链路，不是真实内容。真实内容要把 `.env` 里的
`DEEPSEEK_API_KEY` 填好，并去掉 `--mock`。

**forge 偶尔会重试？**

生成那一步要求模型输出 JSON。格式不对时，`authoring` 会把具体错误拼回提示词、
用同一个 agent 再要一次；两次都错才失败。小模型触发重试更频繁，属正常现象。

**换了模型之后生成质量差？**

生成那一步对 JSON 的服从度比较吃模型能力。对谈环节对模型宽松一些。换模型时优先保证
`forge` 稳定。

**网络/超时问题？**

真实后端已经注入了不联网的 token 计数器并设了超时，避免 camel 默认计数器联网下载
词表时卡住。细节见 [ENGINEERING.md](ENGINEERING.md) 的踩坑记录。
